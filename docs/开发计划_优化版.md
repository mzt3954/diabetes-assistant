## 3. 开源项目参考分析

> **网络说明**：本机 `api.github.com` / `github.com` 连接超时（代理与直连均失败），`WebSearch` 不可用。改由 **Bing 检索（可索引 GitHub）+ Gitee 站内检索**完成调研，下列结论均来自可访问的真实项目页面。

### 3.1 参考项目 A：TangDun — 基于多源数据融合的糖尿病智能健康管理系统

- **定位**：集成 TCN 时序卷积网络（ONNX 推理，MAE 0.552）与 Bergman 生理模型的血糖预测 + 健康管理系统。
- **可借鉴**：
  - **"预测 + 建议"闭环**：模型只输出数值不够，必须紧跟可执行的干预建议——本项目风险预测页据此设计为「评分 → 分档 → 分类归因 → 建议」四段式。
  - **模型与业务解耦**：推理层通过 ONNX 独立部署，前端只调接口——对应本项目把 AI 能力全部收敛到 `api.js` 一层，页面不关心模型细节。
- **需规避**：其依赖重型深度学习栈（PyTorch/ONNX），对"课程实训 + 静态前端"过重，本项目采用**轻量规则评分 + LLM 归因**替代。

### 3.2 参考项目 B：端到端糖尿病预测系统（Pima 数据集 + Flask）

- **技术路径**：皮马印第安人数据集 → 缺失值/异常值处理（IQR）→ StandardScaler 标准化 → SMOTE 处理类别不平衡 → 10 余种模型对比（LR/DT/RF/KNN/GB 朴素贝叶斯/SVM/Voting/Stacking）→ 准确率·精确率·**召回率**·F1·ROC-AUC 多维评估 → Flask 后端 + Glassmorphism 前端。
- **可借鉴**：
  1. **医疗场景以召回率为首要指标**（漏诊代价 > 误诊）→ 本项目风险预测阈值**向下调低**，宁可多报高风险也不漏报，并在 UI 明确"本结果仅供筛查参考，不能替代临床诊断"免责声明。
  2. **置信度分数可视化** → 预测结果页展示风险概率百分比 + 进度环。
  3. **输入即校验** → 表单前置范围校验（年龄 1–120、BMI 合理区间）。
  4. **改进方向**（其作者自述）：引入 SHAP/LIME 可解释性、融合生活方式多模态数据 → 本项目用 **LLM 生成自然语言归因**（"您的风险主要来自 BMI 偏高与家族史"）实现可解释性，成本远低于 SHAP。
- **需规避**：① 数据集来自特定人群（皮马印第安人），**不可直接用于中国人群**——本项目改用中国糖尿病风险评分（CDRS）量表的变量集；② 纯黑盒模型无解释；③ 未做临床验证——必须加免责声明。

### 3.3 参考项目 C：Dify 生态（langgenius/dify 及健康管理类案例）

- **可借鉴**：
  1. **工作流（Workflow）与对话流（Chatflow）分离**：结构化、无多轮上下文的用 Workflow（如风险预测、资讯生成）；需要多轮对话的用 Chatflow（如医师咨询、AI 助手）——本项目 8 个 Dify 应用严格按此原则分工。
  2. **知识库 RAG 作为"事实锚"**：把医学文档灌入知识库，降低大模型幻觉——这正是素材 6 份 docx 的用途。
  3. **`response_mode: streaming` + SSE** 是对话体验的标配——本项目据此实现真正的流式打字机效果（现有代码是 `setInterval` 假打字）。
  4. **Function Calling / 工具调用** 让智能体能操作业务数据——本项目管理助手据此实现"用自然语言增删改数据"。
- **需规避**：直接在前端硬编码 `app-xxx` API Key（会被公开暴露）——本项目把 Key 集中在 `config.js` 并给出**生产环境必须走反向代理**的说明。

### 4.2 缺陷清单

**P0（阻断交付，必须修复）**

1. **AI 能力 0% 落地**。全项目 `fetch` 调用数为 **0**（已全量 grep 验证），Dify 工作流/聊天助手/智能体**一个都没接**。任务 2-3、3-3、5-2、6-2、7-2、8-2、9-2、10-2 共 8 个核心任务未完成。仅存 2 处占位：`life-plan.html:692`、`health-news.html:830` 均为 `alert('...实际项目中将调用Dify工作流API')`。
2. **权限判断不一致（功能性 Bug）**。`index.html` 登录成功后写入 `isAdmin: true/false`；而 `personal.html:1009` 读取 `user.role === 'admin'`。字段名不一致 → **管理员登录后永远看不到"AI智能管理"入口**。
3. **5 个被引用的页面不存在**：`checkin.html`（打卡记录与分析，任务 8 全部）、`admin.html`（智能管理，任务 10 全部）、`help.html`、`article.html`（科普详情）、`diabetes.html`（类型详情）。点击即 404。

**P1（严重影响质量/可维护性）**

4. **样式严重重复**。`.navbar / .bottom-nav / .toast / .modal` 等公共组件在 8 个页面内联重复定义，`common.css` 里已有一份又被各页覆盖。单页内联 `<style>` 达 500–900 行，改一处要改 8 处。
5. **无公共 JS 层**。`getCurrentUser / checkLogin / logout / showToast` 在 8 个文件中各复制一遍；`formatTime` 在 doctor/assistant 重复。
6. **数据层缺失、键名混乱**。mock 数据硬编码在页面内；localStorage 使用 `diabetes_users`、`diabetes_current_user`、`current_article_id`、`current_diabetes_type` 等散乱键名，且与 `db.txt` 表结构不对应。
7. **XSS 注入风险**。聊天消息、用户名等用户输入经 `innerHTML` 直接拼接（如 `personal.html:1099`、`doctor.html` 消息渲染），无转义。
8. **无错误处理与降级**。无超时、无重试、无网络失败兜底；模拟请求统一 `setTimeout(800)` 假延迟。

**P2（优化项）**

9. 无统一 API 配置入口，Dify Base URL / Key 无处可填。
10. 可访问性不足：`<label>` 未 `for` 关联、图标按钮无 `aria-label`、模态框无焦点管理。
11. 表单校验规则分散且不一致（登录密码 ≥6 位，注册用户名 ≥3 位，但提示文案不统一）。
12. 代码风格不统一：`onclick=` 内联事件与 `addEventListener` 混用；`function` 与箭头函数混用。
13. 无版本/缓存管理，静态资源无 hash。

```

├─────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────┤
│  服务层  js/api.js   Dify 客户端（Workflow/Chat/SSE 流式/   │
```

### 5.3 关键设计：双模式运行（离线可演示 ⇄ 在线真 AI）

这是本项目区别于原实现的核心设计，同时满足"**必须接入 Dify**"与"**必须可直接运行**"两个看似冲突的要求：

```
                 ┌── config.js: USE_MOCK = true  或  API Key 未配置
                 │        └→ mock-engine.js  本地规则引擎（零依赖，离线可用）
请求 → api.js ───┤
                 └── config.js: USE_MOCK = false 且 API Key 已配置
                          └→ Dify HTTP API（Workflow / Chatflow / SSE 流式）
                          └→ 若请求失败/超时 → 自动降级到 mock-engine 并 Toast 提示
```

- **演示/答辩场景**：无需部署 Dify，克隆即跑，所有功能有真实可用的输出。
- **生产场景**：填入 Dify Base URL 与 App Key，一键切换为真实大模型能力。
- **鲁棒性**：Dify 宕机时自动降级，不会白屏。

### 5.4 数据流（以风险预测为例）

```
用户填表 → risk.js 表单校验 → store.saveUserRiskInfo() 落库
   → api.runWorkflow('risk_prediction', inputs)
        ├─ [在线] POST {DIFY_BASE}/v1/workflows/run  {response_mode:'blocking'}
        └─ [离线] mockEngine.predictRisk(inputs)   ← CDRS 评分算法
   → 返回 {score, level, probability, disease, message, advice[]}
   → 渲染结果卡片（概率环 + 分档徽章 + LLM 归因 + 建议列表 + 免责声明）
   → store 记录历史，个人中心可回看
```

## 8. 关键技术实现方案

### 8.1 Dify API 客户端（`js/api.js`）

```js
// 工作流（阻塞式）
POST {BASE}/v1/workflows/run
Headers: { Authorization: 'Bearer app-xxx', 'Content-Type': 'application/json' }
Body:    { inputs:{...}, response_mode:'blocking', user:'<username>' }
Resp:    { data:{ status:'succeeded', outputs:{...} } }

// 对话（流式 SSE）
POST {BASE}/v1/chat-messages
Body:    { inputs:{}, query, response_mode:'streaming', conversation_id:'', user }
SSE 事件: message(answer 增量) / agent_message / message_end(conversation_id,metadata) / error / ping
```
实现要点：`fetch` + `response.body.getReader()` + `TextDecoder` 逐块解析 `data: {...}`，支持 `AbortController` 中断，超时 30s，失败重试 1 次后降级。

### 8.2 糖尿病风险预测算法（`mock-engine.js`，本地兜底）

参考**中国糖尿病风险评分（CDRS）**变量集，采用加权累加：

| 变量 | 分档 | 分值 |
|------|------|------|
| 年龄 | <40 / 40–49 / 50–59 / ≥60 | 0 / 2 / 4 / 6 |
| BMI | <24 / 24–27.9 / ≥28 | 0 / 3 / 5 |
| 腰围(cm) | 男<90 女<85 / 超标 | 0 / 3 |
| 家族史 | 无 / 有 | 0 / 5 |
| 收缩压(mmHg) | <130 / ≥130 | 0 / 3 |
| 性别 | 女 / 男 | 0 / 1 |
| 妊娠史 | 无 / 有（女性） | 0 / 4 |

总分 0–27 分：**<9 低风险｜9–15 中风险｜≥16 高风险**。高风险者按"妊娠型（有妊娠史）/ 2 型（BMI+家族史为主）/ 特殊型（继发因素）"做归因分类。
⚠️ **医疗安全**：界面强制展示"本结果基于风险量表筛查，仅供健康参考，不能替代临床诊断，请及时就医"。

### 8.3 打卡分析算法（`mock-engine.js`）

三维指标：**完成率** = 已打卡项 / 应打卡项；**连续天数** = 近 7 日最长连续打卡；**类型均衡度** = min(饮食完成率, 运动完成率)。
评级：完成率 ≥85% → 优秀；60%–85% → 良好；<60% → 需改进。评价与建议由 WF-5 或本地模板生成。

### 8.4 角色权限矩阵

| 能力 | 游客 | 普通用户 | 管理员 |
|------|------|---------|--------|
| 浏览首页/科普/类型 | ✅ | ✅ | ✅ |
| 风险预测 / 生活方案 / 打卡 / 资讯 / 助手 | ❌ | ✅ | ✅ |
| 个人资料编辑 | ❌ | ✅ | ✅ |
| 进入 AI 智能管理 | ❌ | ❌ | ✅ |
| 自然语言增删改数据 | ❌ | ❌ | ✅ |

统一由 `auth.js` 的 `requireAuth()` / `requireAdmin()` 守卫，**角色字段统一为 `role: 'user' | 'admin'`**（修复 P0-2）。

## 9. 非功能性需求落地方案

| 需求（原文） | 技术实现 |
|-------------|---------|
| 1 秒内返回，最多 3 秒 | 首屏静态渲染 + 骨架屏；AI 调用走 SSE 流式，首字延迟 <1s；非 AI 数据本地读取 <50ms |
| 数据同步 1s 内 | localStorage 同步写；写入即回读校验 |
| 7×24 可用 | 纯静态 + Nginx，无后端单点；Dify 故障自动降级 |
| 健壮性（异常输入） | 统一表单校验 + 数值范围钳制 + `try/catch` 全局兜底 + 空状态页 |
| 安全性（数据加密/权限） | 密码 SHA-256 摘要存储（不存明文）；所有 `innerHTML` 经 `escapeHtml()` 转义防 XSS；角色守卫；生产环境 API Key 走反向代理 |
| 易用性/记忆负担 | 统一设计系统、一致交互、底部导航常驻、Toast 即时反馈 |
| 可扩展性 | 分层架构，新增页面只需 +1 HTML +1 JS；新增 AI 能力只需在 `config.js` 注册应用 |
| 兼容性 | ES6+ + CSS 变量，兼容 Chrome/Edge/Firefox/Safari 最近两版；响应式 3 断点（480/768/1200） |
| 可移植性 | 零构建、零依赖，拷贝即用；`npx http-server` 或 Nginx 均可 |
