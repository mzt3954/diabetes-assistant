# 用户数据持久化方案（Express + MySQL）

> 糖尿病预治智能助手 · 2026 秋 实训 2
> 最后验证：2026-09-18 12:45 ｜ 环境：MySQL 8.4.9 / Node 22.22.2 / Windows 11

---

## 0. 一句话说明

系统原本把用户存在浏览器 localStorage 里。本方案新增了一套 **Express + MySQL**
后端，把用户数据落到真正的数据库表中，并让前端**自动切换**：

- 后端在 → 登录、注册、改资料、删账号全部走 MySQL（数据库是权威来源）
- 后端不在 → 自动降级回 localStorage，功能完全不受影响（离线演示模式）

两种模式对页面代码是透明的，前端既有 273 条自动化测试全部保持通过。

---

## 1. 整体架构

```
   浏览器页面（同步读）
        │
        │  DPA.store.users  ← localStorage：同步缓存
        │        ▲   │
        │  镜像  │   │  写穿透（store.onUsersChanged 钩子）
        │        │   ▼
        │   DPA.db（js/db-client.js）
        │        │
        │        │  HTTP / JSON
        │        ▼
   server/index.js  ──►  server/routes/auth.js   注册 / 登录
        │                 server/routes/users.js  CRUD
        │                 server/model.js         校验 + 脱敏
        │                 server/db.js            连接池（参数化查询）
        │                 server/password.js      scrypt 口令派生
        │                        │
        │                        ▼
        └──────────────►  MySQL 8.4  diabetes_assistant
                            ├── users        用户表
                            └── login_logs   登录日志表
```

**为什么要「localStorage + MySQL」两层？**

前端既有 API 全是**同步**的（`DPA.auth.login()` 被 273 条测试同步调用）。
HTTP 是异步的，直接改造会把所有调用方一起改掉、测试全挂。
所以采用「**本地同步缓存 + 数据库真源**」：

| 关注点 | 承担者 |
| --- | --- |
| 页面读取用户、渲染列表 | localStorage（同步、零延迟） |
| 数据持久化、唯一性约束、口令校验 | MySQL（真源） |
| 后端不可用时的可用性 | localStorage 降级 |
| 登录/注册的权威判定 | MySQL（用同步 XHR 保证同步语义） |

## 2. 表结构设计

数据库：`diabetes_assistant`，字符集 `utf8mb4` / 排序规则 `utf8mb4_unicode_ci`
（中文用户名、中文枚举值 `男`/`女`/`2型糖尿病` 都能正确存取）。

### 2.1 `users` —— 用户表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `user_id` | `INT UNSIGNED` | **主键 PK**，`AUTO_INCREMENT` | — | 用户 ID，自增 |
| `username` | `VARCHAR(50)` | **唯一键 UK**，`NOT NULL` | — | 登录用户名，全局唯一 |
| `password_hash` | `VARCHAR(128)` | `NOT NULL` | — | scrypt 派生密钥（64 字节 → 128 位十六进制） |
| `password_salt` | `CHAR(32)` | `NOT NULL` | — | 口令随机盐（16 字节 → 32 位十六进制） |
| `role` | `ENUM('user','admin')` | `NOT NULL`，普通索引 | `'user'` | 角色：普通用户 / 管理员 |
| `phone` | `VARCHAR(20)` | 可空 | `NULL` | 手机号（选填） |
| `age` | `TINYINT UNSIGNED` | 可空 | `NULL` | 年龄（选填，业务校验 1~120） |
| `gender` | `ENUM('男','女')` | 可空 | `NULL` | 性别（选填） |
| `diabetes_type` | `VARCHAR(32)` | 可空 | `NULL` | 糖尿病类型（选填，5 种取值） |
| `avatar_url` | `VARCHAR(255)` | `NOT NULL` | `''` | 头像地址（选填） |
| `status` | `TINYINT` | `NOT NULL` | `1` | 账号状态：1 正常 / 0 停用 |
| `create_time` | `DATETIME` | `NOT NULL` | `CURRENT_TIMESTAMP` | 创建时间，自动填充 |
| `update_time` | `DATETIME` | `NOT NULL` | `CURRENT_TIMESTAMP ON UPDATE` | 最后更新时间，自动维护 |

**索引设计**

| 索引名 | 类型 | 字段 | 用途 |
| --- | --- | --- | --- |
| `PRIMARY` | 主键 | `user_id` | 按 ID 查用户 |
| `uk_users_username` | 唯一 | `username` | 登录查询 + **数据库层保证用户名不重复** |
| `idx_users_role` | 普通 | `role` | 按角色筛选（管理端） |
| `idx_users_create_time` | 普通 | `create_time` | 按注册时间排序 / 统计 |

**设计要点**

1. **口令永不落明文**：只存 `password_salt` + `password_hash`。
   算法为 Node 内置 `crypto.scrypt`（`N=16384, r=8, p=1, keylen=64`），
   内存硬化，抗 GPU 暴力破解；比原先前端的「SHA-256 迭代 1000 次」强得多。
2. **用户名唯一性交给数据库**：应用层先查一次给出友好提示，
   但真正的兜底是唯一索引 —— 并发注册也不会出现两个同名账号。
3. **`age` 用 `TINYINT UNSIGNED`**：0~255，业务层再限制到 1~120。
4. **`status` 支持停用**：登录时校验，被停用的账号即使口令正确也拒绝。
5. **`update_time` 由数据库自动维护**，不依赖应用代码，不会漏更新。

### 2.2 `login_logs` —— 登录日志表

| 字段名 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `log_id` | `BIGINT UNSIGNED` | **主键 PK**，`AUTO_INCREMENT` | 日志 ID |
| `user_id` | `INT UNSIGNED` | 可空，**外键** → `users.user_id` | 用户 ID（登录失败时为空） |
| `username` | `VARCHAR(50)` | `NOT NULL` | 本次尝试登录的用户名 |
| `success` | `TINYINT(1)` | `NOT NULL`，默认 0 | 是否成功：1 成功 / 0 失败 |
| `ip` | `VARCHAR(45)` | 可空 | 客户端 IP（45 位兼容 IPv6） |
| `user_agent` | `VARCHAR(255)` | 可空 | 客户端 User-Agent |
| `login_time` | `DATETIME` | `NOT NULL`，默认 `CURRENT_TIMESTAMP` | 登录时间 |

**外键行为**：`ON DELETE SET NULL ON UPDATE CASCADE`

- 删除用户时，日志的 `user_id` 置为 `NULL`，**日志本身保留** —— 审计记录不能因为
  删号就消失。
- 登录成功与失败**都**写日志（失败记录 `user_id` 为空），可用于发现暴力破解。

## 3. 完整建库建表语句

文件位置：`server/sql/01-schema.sql`（可直接复制到 MySQL 客户端执行）

```sql
-- ============================================================================
--  糖尿病预治智能助手 · 用户数据持久化
--  01-schema.sql —— 建库建表（幂等，可重复执行）
-- ============================================================================

CREATE DATABASE IF NOT EXISTS `diabetes_assistant`
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_unicode_ci;

USE `diabetes_assistant`;

-- ---------------------------------------------------------------------------
-- 用户表
-- ---------------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS `users` (
  `user_id`       INT UNSIGNED         NOT NULL AUTO_INCREMENT           COMMENT '用户ID，主键，自增',
  `username`      VARCHAR(50)          NOT NULL                          COMMENT '登录用户名，全局唯一',
  `password_hash` VARCHAR(128)         NOT NULL                          COMMENT '口令派生密钥（scrypt，64字节→128位十六进制）',
  `password_salt` CHAR(32)             NOT NULL                          COMMENT '口令随机盐（16字节→32位十六进制）',
  `role`          ENUM('user','admin') NOT NULL DEFAULT 'user'           COMMENT '角色：user 普通用户 / admin 管理员',
  `phone`         VARCHAR(20)          DEFAULT NULL                      COMMENT '手机号码（选填）',
  `age`           TINYINT UNSIGNED     DEFAULT NULL                      COMMENT '年龄（选填，业务校验 1~120）',
  `gender`        ENUM('男','女')      DEFAULT NULL                      COMMENT '性别（选填）',
  `diabetes_type` VARCHAR(32)          DEFAULT NULL                      COMMENT '糖尿病类型（选填）',
  `avatar_url`    VARCHAR(255)         NOT NULL DEFAULT ''               COMMENT '头像地址（选填）',
  `status`        TINYINT              NOT NULL DEFAULT 1                COMMENT '账号状态：1 正常 / 0 停用',
  `create_time`   DATETIME             NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time`   DATETIME             NOT NULL DEFAULT CURRENT_TIMESTAMP
                                       ON UPDATE CURRENT_TIMESTAMP       COMMENT '最后更新时间',
  PRIMARY KEY (`user_id`),
  UNIQUE KEY `uk_users_username` (`username`),
  KEY `idx_users_role` (`role`),
  KEY `idx_users_create_time` (`create_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci
  COMMENT = '用户表：保存系统全部用户的账号与基础资料';

-- ---------------------------------------------------------------------------
-- 登录日志表
-- ---------------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS `login_logs` (
  `log_id`     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT   COMMENT '日志ID，主键，自增',
  `user_id`    INT UNSIGNED    DEFAULT NULL              COMMENT '用户ID（登录失败时为空）',
  `username`   VARCHAR(50)     NOT NULL                  COMMENT '本次尝试登录的用户名',
  `success`    TINYINT(1)      NOT NULL DEFAULT 0        COMMENT '是否成功：1 成功 / 0 失败',
  `ip`         VARCHAR(45)     DEFAULT NULL              COMMENT '客户端IP（兼容 IPv6）',
  `user_agent` VARCHAR(255)    DEFAULT NULL              COMMENT '客户端 User-Agent',
  `login_time` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '登录时间',
  PRIMARY KEY (`log_id`),
  KEY `idx_login_logs_user` (`user_id`),
  KEY `idx_login_logs_time` (`login_time`),
  CONSTRAINT `fk_login_logs_user`
    FOREIGN KEY (`user_id`) REFERENCES `users` (`user_id`)
    ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci
  COMMENT = '用户登录日志表：记录登录尝试，用于安全审计';
```

种子数据见 `server/sql/02-seed.sql`（4 个演示账号 + 3 条登录日志样例）。

## 4. 数据库连接配置说明

### 4.1 配置文件

连接参数集中在 `server/.env`（模板：`server/.env.example`）。
读取顺序：**进程环境变量 > `server/.env` > 代码默认值**。

`server/.env` 内容（本机 root 无密码环境）：

```ini
# ---------- HTTP 服务 ----------
SERVER_HOST=127.0.0.1        # 127.0.0.1 仅本机；0.0.0.0 允许局域网
SERVER_PORT=8090             # API 与前端静态站点共用同一端口
SERVE_STATIC=1               # 1 同时托管前端；0 只提供 API

# ---------- MySQL 连接 ----------
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=root
DB_PASSWORD=                 # 本机 root 无密码，留空即可
DB_NAME=diabetes_assistant
DB_POOL_SIZE=10              # 连接池大小

# ---------- 启动行为 ----------
AUTO_INIT_DB=0               # 1 = 启动时自动建库建表 + 写种子数据
```

> **口令为空串的处理**：`server/config.js` 用 `process.env.DB_PASSWORD === undefined`
> 判断，而不是 `|| ''`。否则「显式配置成空串」与「没配置」无法区分，
> 会错误地退回默认值。

### 4.2 连接池参数（`server/db.js`）

| 参数 | 值 | 原因 |
| --- | --- | --- |
| `connectionLimit` | 10 | 复用 TCP 连接，避免每次请求重新握手 |
| `charset` | `utf8mb4` | 中文用户名、中文枚举值 |
| `dateStrings` | `true` | `DATETIME` 直接以字符串返回，避免 Node 与 MySQL 时区差 8 小时 |
| `multipleStatements` | `false` | **防 SQL 注入**：禁止一次执行多条语句 |
| 参数传递 | 全部 `?` 占位符 | 由驱动做转义，从根本上杜绝注入 |

### 4.3 前置条件

```bash
# 1) MySQL 已启动并监听 3306
netstat -ano | findstr :3306

# 2) 装依赖（express + mysql2）
npm install

# 3) 建库建表 + 种子数据
npm run db:init
```

## 5. CRUD 操作实现

### 5.1 代码分层

| 文件 | 职责 |
| --- | --- |
| `server/config.js` | 读取环境变量 / `.env`，产出配置对象 |
| `server/db.js` | MySQL 连接池；`query` / `execute` / `withTransaction` / `healthCheck` / `stats` |
| `server/password.js` | scrypt 口令派生与恒定时间比较 |
| `server/model.js` | 字段校验、取值规范化、`toPublicUser` 脱敏、可改字段白名单 |
| `server/routes/auth.js` | 注册、登录（含登录日志） |
| `server/routes/users.js` | 用户 CRUD（列表/详情/新建/更新/删除） |
| `server/app.js` | Express 装配：CORS、访问日志、路由挂载、静态托管、统一错误处理 |
| `server/index.js` | 启动入口：探活数据库、监听端口、优雅退出 |
| `server/init-db.js` | 建库建表脚本（`--schema` / `--check`） |

### 5.2 接口清单

| 方法 | 路径 | 说明 | 成功状态码 |
| --- | --- | --- | --- |
| `GET` | `/api/health` | 健康检查（数据库连通性 + 各表行数） | 200 |
| `POST` | `/api/auth/register` | 注册（用户名唯一，口令 scrypt 后入库） | 201 |
| `POST` | `/api/auth/login` | 登录（校验口令与账号状态，写登录日志） | 200 |
| `GET` | `/api/users` | 用户列表，支持 `page` / `pageSize` / `keyword` / `role` | 200 |
| `GET` | `/api/users/:id` | 用户详情 | 200 |
| `POST` | `/api/users` | 新建用户（管理端） | 201 |
| `PUT` | `/api/users/:id` | 更新资料（白名单字段） | 200 |
| `DELETE` | `/api/users/:id` | 删除用户 | 200 |

**统一响应格式**

```jsonc
// 成功
{ "ok": true,  "data": { ... } }
// 失败
{ "ok": false, "error": { "code": "INVALID_PHONE", "message": "手机号格式不正确" } }
```

**错误码对照**

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `INVALID_USERNAME` / `INVALID_PASSWORD` / `INVALID_PHONE` / `INVALID_AGE` / `INVALID_GENDER` / `INVALID_DIABETES_TYPE` | 字段校验失败 |
| 400 | `BAD_JSON` | 请求体不是合法 JSON |
| 401 | `INVALID_CREDENTIALS` | 用户名或口令错误（不区分两者，防用户枚举） |
| 404 | `USER_NOT_FOUND` | 用户不存在 |
| 409 | `USERNAME_TAKEN` | 用户名已存在 |
| 500 | `SCHEMA_MISSING` | 数据表不存在（提示先跑 `npm run db:init`） |
| 503 | `DB_UNAVAILABLE` | 连不上 MySQL |

### 5.3 SQL 语句一览

**Create**

```sql
INSERT INTO users (username, password_hash, password_salt, role, status,
                   phone, age, gender, diabetes_type, avatar_url)
VALUES (?, ?, ?, ?, 1, ?, ?, ?, ?, ?);
```

**Read（列表，含分页与筛选）**

```sql
-- 先数总数（用于分页）
SELECT COUNT(*) AS total FROM users
WHERE (username LIKE ? OR phone LIKE ?) AND role = ?;

-- 再取当页数据（page / pageSize 已确保为安全整数，直接内插，
-- 因为 mysql2 的 execute 不支持在 LIMIT / OFFSET 上使用占位符）
SELECT * FROM users
WHERE (username LIKE ? OR phone LIKE ?) AND role = ?
ORDER BY user_id ASC
LIMIT 20 OFFSET 0;
```

> 查询用 `SELECT *`，但**出口统一经过 `model.toPublicUser()` 脱敏**，
> `password_hash` / `password_salt` 不会出现在任何响应里。

**Read（详情 / 登录查询）**

```sql
SELECT * FROM users WHERE user_id = ?;            -- 详情
SELECT * FROM users WHERE username = ? LIMIT 1;   -- 登录（需要拿到口令哈希做校验）
```

**Update（白名单字段动态拼接）**

```sql
UPDATE users SET phone = ?, age = ?, gender = ?, diabetes_type = ?, avatar_url = ?
WHERE user_id = ?;
```

**Delete**

```sql
DELETE FROM users WHERE user_id = ?;
```

**登录日志**

```sql
INSERT INTO login_logs (user_id, username, success, ip, user_agent)
VALUES (?, ?, ?, ?, ?);
```

### 5.4 安全设计（服务端独立校验）

| 措施 | 实现 |
| --- | --- |
| 口令不落明文 | scrypt（`N=16384, r=8, p=1, keylen=64`）+ 16 字节随机盐 |
| 恒定时间比较 | `crypto.timingSafeEqual`，避免通过响应时间猜口令 |
| 防用户枚举 | 用户不存在时也执行一次等价耗时的哈希运算，响应时间无差别 |
| 防 SQL 注入 | 全部 `?` 占位符 + `multipleStatements: false` |
| 防越权改字段 | `UPDATABLE_FIELDS` 白名单；`role` / `password` / `status` 被挡下并在响应 `rejected` 中列出 |
| 响应体脱敏 | `toPublicUser()` 只输出业务字段，**永不返回** `password_hash` / `password_salt` |
| 静态托管隔离 | 正则 `^\/(server\|node_modules\|\.env\|\.git)(\/\|$)` 直接 403，`.env` 与 SQL 不会被 HTTP 读到 |
| CORS 收紧 | 只放行 `^https?://(127\.0\.0\.1\|localhost)(:\d+)?$` |

## 6. 与后端代码的集成方式

### 6.1 服务端：路由 → 模型 → 数据访问

```
HTTP 请求
   │
   ▼
server/app.js          统一中间件（JSON 解析 256KB 上限、CORS、访问日志）
   │
   ▼
server/routes/*.js     参数接收 → 调 model 校验 → 调 db 执行 → 统一响应
   │                       │                        │
   │                       ▼                        ▼
   │              server/model.js            server/db.js
   │              （校验 / 规范化 / 脱敏）      （连接池 / 参数化查询）
   │                                                 │
   ▼                                                 ▼
server/app.js 的错误中间件  ◄──  ER_DUP_ENTRY→409 / ER_NO_SUCH_TABLE→SCHEMA_MISSING
   │                                              / ECONNREFUSED→503
   ▼
JSON 响应
```

**启动入口 `server/index.js` 做四件事**

1. 读配置（`config.js`）
2. `AUTO_INIT_DB=1` 时先执行 `init-db.js`（一条命令从零到可用）
3. 探活数据库 —— **连不上也照常启动**，只是把原因和修复建议打印清楚，
   涉及数据库的接口返回 503。这样前端页面仍然能打开，不会白屏。
4. 监听端口 + `SIGINT`/`SIGTERM` 优雅关闭连接池

### 6.2 前端：同步缓存 + 写穿透 + 自动降级

新增一个模块 `js/db-client.js`（`DPA.db`），它做四件事：

| 能力 | 实现 | 为什么这样做 |
| --- | --- | --- |
| **探测** | 页面加载时异步 `GET /api/health`，之后每 15 秒重探一次 | 后端后启动也能自动接上；探测失败即彻底退回本地模式 |
| **同步登录/注册** | 同步 `XMLHttpRequest` | 保证 `DPA.auth.login()` 仍是同步函数，273 条测试不受影响 |
| **写穿透** | 订阅 `store.onUsersChanged` 钩子，异步对账后 PUT/POST 到数据库 | 各页面代码一行都不用改 |
| **镜像回填** | `store.users.replaceAllFromDb()` / `mirrorFromDb()` | 管理端列表、个人中心读的仍是本地表，但内容与数据库一致 |

**自动降级的判定**

| 打开方式 | 同源探测 | 结果 |
| --- | --- | --- |
| `http://127.0.0.1:8090/index.html` | 命中后端 | **数据库模式** |
| `http://127.0.0.1:8080/index.html`（契约桩托管前端） | 404 | 本地降级模式 |
| `file:///.../index.html` | 失败 | 本地降级模式 |
| jsdom / Node 测试环境 | 主动关闭 | 本地模式（保证测试确定性） |

**登录逻辑（`js/auth.js`）**

```js
login: function (username, password, persist) {
  var d = global.DPA.db;
  if (d) {
    var r = d.loginSync(username, password);          // 同步 XHR → MySQL
    if (r && r.status === 'ok')       { /* 登录成功，来源 database */ }
    if (r && r.status === 'rejected') { /* 服务端明确拒绝，不再降级 */ }
    /* r.status === 'offline' → 落到下面 */
  }
  var user = store.users.verify(username, password);  // 降级：本地校验
  ...
}
```

关键点：**服务端明确说「口令错误」时不再降级**。
否则数据库里的口令校验就形同虚设 —— 错口令仍能靠本地记录登录。

**离线兜底**：数据库登录成功后，会把这条记录镜像进本地并补一份本地口令哈希
（`mirrorFromDb(user, plainPassword)`）。这样断网后同一账号仍能登录。
数据库里只存 scrypt 哈希，前端算法不同无法复用，所以必须借这次已验证的明文补写。

### 7.4 常见问题

| 现象 | 原因 | 处理 |

## 9. 已知局限（答辩可主动说明）

1. **无会话令牌**。登录成功后前端只在本地记会话，后续接口没有做身份鉴权。
   生产系统应签发 JWT / Session，并给写接口加鉴权中间件。
2. **`PUT` / `DELETE` 未鉴权**。任何人都能调 `/api/users/:id` 改资料、删账号。
   课程演示范围内可接受，生产环境必须加管理员校验。
3. **同步 XHR 已不推荐**。它是为兼容既有同步 API 与 273 条测试而做的妥协。
   理想方案是把 `auth.login` 改成 async，全面改用 `fetch`。
4. **HTTP 明文**。演示环境走 `http://127.0.0.1`，生产应启用 HTTPS。
5. **未做口令强度策略**。目前只校验长度 ≥6，没有复杂度要求与失败锁定。
