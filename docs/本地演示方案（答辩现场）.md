# 本地演示方案（答辩现场专用）

> 目标：在**不依赖课程云沙箱、不依赖外网**的前提下，通过 VS Code 一键启动本项目，并让前端与 Dify 接口链路完整可用，保证答辩现场演示零失败。
>
> 适用项目：糖尿病预治智能助手（`diabetes-assistant` v2.1.0）
> 最后验证时间：2026-09-17 23:5x（Node v22.22.2 / npm 10.9.7 / Windows）

## 一、结论速览

| 项目 | 结论 |
|---|---|
| 演示是否依赖外网 | **不依赖**。提供「本地契约桩」与「纯离线引擎」两种零外网方案 |
| 演示是否依赖真实 Dify 实例 | **不依赖**。本地契约桩 1:1 复刻 Dify 的鉴权、请求体、响应结构与 SSE 事件序列 |
| 启动方式 | VS Code 按 `F5`（或 `Ctrl+Shift+P → Tasks: Run Task`） |
| 首推配置 | `演示 · 本地契约桩（Chrome）` —— 一键完成「起服务 + 开浏览器」 |
| 站点地址 | `http://127.0.0.1:8080/index.html` |
| 演示账号 | `admin / admin123`（管理员）、`user / user123`（普通用户） |
| 前端运行时依赖 | **零**。纯静态站点，无构建步骤、无 npm 运行时依赖 |

**核心设计原则**：项目本身具备**双模式运行**能力。配置了可用 Dify 就走向真实大模型；未配置、请求失败或输出契约不匹配时，自动降级到 `js/mock-engine.js` 本地规则引擎，页面仅弹出 Toast 提示而**不会白屏**。因此答辩现场最坏情况也只是"降级演示"，不会中断。

> **⚠️ 已修复的演示隐患（务必知悉）**
> 桩服务与生产 Nginx 均下发 CSP 指令 `script-src 'self'`（不含 `'unsafe-inline'`），而项目原有 8 个页面各含一段**内联 `<script>`**，会被浏览器**静默拦截**，导致「近 7 日打卡趋势折线图」「热门资讯浏览量条形图」「生活方案进度环形图」以及各页错误态保护逻辑**全部失效**。已通过将内联脚本抽取为外链文件修复，详见 §7 问题 8。

项目提供三种模式，由 `tools/demo-mode.js` 一键切换（改写 `js/config.local.js`）。

| 模式 | 命令 | 数据来源 | 是否需外网 | 演示效果 | 适用场景 |
|---|---|---|---|---|---|

| **B. 纯离线引擎** | `demo-mode.js offline` | `js/mock-engine.js` 本地规则 | 否 | 功能完整，但无流式输出、网络面板无请求 | 桩服务异常时兜底 |
| **C. 课程云沙箱** | `demo-mode.js sandbox` | `123.249.115.157:48823` | **是** | 真实 DeepSeek 大模型输出 | 仅在沙箱恢复可用时 |

### 3.1 为什么首选「本地契约桩」

**实测结论：课程云沙箱当前不可达。**

```bash
$ curl -s -m 5 -o /dev/null -w "%{http_code}" --noproxy '*' \
    http://123.249.115.157:48823/v1/parameters
502
```

沙箱返回 **HTTP 502（Bad Gateway）**，说明网关后的 Dify 实例已下线或端口变更。**若答辩现场依赖沙箱，演示必然失败。**

本地契约桩（`tests/mock-dify-server.js`）解决了这个问题，它**契约忠实**地复刻了真实 Dify：

- ✅ 校验 `Authorization: Bearer <key>`，无 Key 返回 401
- ✅ 按 API Key 区分 8 个应用（Key 与应用的映射关系同真实 Dify）
- ✅ 工作流返回**阻塞式**标准结构：`{ workflow_run_id, data: { status: "succeeded", outputs: {...} } }`
- ✅ 对话流返回**标准 SSE 事件序列**：`message` → `message_end`（打字机效果可正常演示）
- ✅ 响应体结构与字段名与真实 Dify 完全一致，前端代码**无需任何改动**
- ✅ 支持故障注入（用于演示降级路径）
- ✅ 可同时托管静态站点，**单端口 8080 同时提供页面与 API**，彻底规避跨域问题

## 五、Dify 对接方式与参数配置位置

### 5.1 配置的层级结构

项目采用**两级配置 + 本地覆盖**的设计：

```
js/config.js                ← 配置主入口（提交入库，不含任何密钥）
   └─ CONFIG.DIFY           ← Dify 参数定义在此
        ↑ 被覆盖
js/config.local.js          ← 本地覆盖（.gitignore 排除，由 demo-mode.js 生成）
   └─ window.DPA_CONFIG_LOCAL ← 页面加载时覆盖 CONFIG
```

`js/config.js` 末尾的覆盖逻辑：

```js
// 读取本地覆盖配置
if (typeof LOCAL.USE_MOCK === 'boolean') CONFIG.USE_MOCK = LOCAL.USE_MOCK;
if (LOCAL.DIFY) {
  if (LOCAL.DIFY.baseUrl)  CONFIG.DIFY.baseUrl  = LOCAL.DIFY.baseUrl;
  if (typeof LOCAL.DIFY.proxyMode === 'boolean') CONFIG.DIFY.proxyMode = LOCAL.DIFY.proxyMode;
  // ...逐应用覆盖 apiKey
}
```

> **为什么这样设计**：`config.js` 入库、密钥不入库。`config.local.js` 已在 `.gitignore` 中排除，避免真实 API Key 泄露到代码仓库。这是本项目安全评审的一项整改措施。

### 5.2 Dify 参数详解（`js/config.js` → `CONFIG.DIFY`）

```js
DIFY: {
  baseUrl: '',          // ① Dify API 基地址，须以 /v1 结尾
  proxyMode: false,     // ② 反向代理模式开关
  timeout: 60000,       // ③ 单次请求超时（毫秒）
  retry: 1,             // ④ 失败重试次数
  apps: {
    // ⑤ 8 个应用的 API Key，key 为应用标识，type 决定调用端点
    homeData:        { key: 'WF-1',    name: '首页数据管理',     type: 'workflow', apiKey: '' },
    doctorChat:      { key: 'CHAT-1',  name: '医师咨询助手',     type: 'chat',     apiKey: '' },
    riskPrediction:  { key: 'WF-2',    name: '个人信息与风险预测', type: 'workflow', apiKey: '' },
    lifePlan:        { key: 'WF-3',    name: '生活方案定制',     type: 'workflow', apiKey: '' },
    healthNews:      { key: 'WF-4',    name: '健康资讯生成',     type: 'workflow', apiKey: '' },
    checkinAnalysis: { key: 'WF-5',    name: '打卡分析',         type: 'workflow', apiKey: '' },
    aiAssistant:     { key: 'CHAT-2',  name: 'AI智能助手',       type: 'chat',     apiKey: '' },
    adminAgent:      { key: 'AGENT-1', name: 'AI管理助手',       type: 'agent',    apiKey: '' }
  }
}
```

**各参数说明：**

| 参数 | 类型 | 作用 | 本地桩取值 | 沙箱取值 |
|---|---|---|---|---|
| `baseUrl` | string | Dify API 基地址，**必须含 `/v1` 后缀** | `http://127.0.0.1:8080/v1` | `http://123.249.115.157:48823/v1` |
| `proxyMode` | boolean | `true` 时密钥由 Nginx 注入，前端不填 `apiKey` | `false` | `false` |
| `timeout` | number | 请求超时毫秒数 | `60000` | `60000` |
| `retry` | number | 失败重试次数 | `1` | `1` |
| `apps.*.type` | enum | **决定调用哪个端点**（见 §5.4） | — | — |
| `apps.*.apiKey` | string | 应用密钥，**必须以 `app-` 开头** | `app-wf-home-key` 等 | `app-<24位随机串>` 等 |

### 5.3 三种对接模式

| 模式 | 配置方式 | 密钥位置 | 适用场景 |
|---|---|---|---|
| **A. 直连** | `baseUrl` 填 Dify 地址 + `apiKey` 明文填写 | 前端 `config.local.js` | 本地开发、教学演示（**需 Dify 侧配置 CORS 白名单**） |
| **B. 反向代理** | `baseUrl: '/v1'` + `proxyMode: true` | Nginx 注入，前端不填 | 生产部署（密钥不暴露给浏览器） |
| **C. 本地契约桩** | `baseUrl: 'http://127.0.0.1:8080/v1'` + 桩服务 Key | 桩服务内置映射表 | **答辩现场（本方案推荐）** |

### 5.4 应用类型与端点的对应关系（关键）

前端 `js/api.js` 依据 `type` 字段选择调用端点：

| `type` | 调用端点 | 响应方式 | 前端处理 |
|---|---|---|---|
| `workflow` | `POST {baseUrl}/workflows/run` | **阻塞式**，一次返回完整 JSON | 解析 `data.outputs` |
| `chat` | `POST {baseUrl}/chat-messages` | **流式 SSE** | `ReadableStream` + `TextDecoder` 逐块解析，实现打字机效果 |
| `agent` | `POST {baseUrl}/chat-messages` | 流式 SSE | 同 chat |

**请求头统一为：**

```
Authorization: Bearer <apiKey>
Content-Type: application/json
```

**工作流请求体（示例）：**

```json
{
  "inputs": { "age": 45, "bmi": 26.3, "fastingGlucose": 6.8 },
  "response_mode": "blocking",
  "user": "user-001"
}
```

**对话流请求体（示例）：**

```json
{
  "inputs": {},
  "query": "糖尿病前期应该怎么调整饮食？",
  "response_mode": "streaming",
  "conversation_id": "",
  "user": "user-001"
}
```

> **配置位置速查**：想改 Dify 地址或密钥，**只改 `js/config.local.js` 一个文件**即可（或用 `node tools/demo-mode.js <mode>` 自动生成）。不需要动 `config.js`。

### 5.5 就绪判定逻辑（决定是否走在线模式）

`CONFIG.isDifyReady(appId)` 与 `CONFIG.isOnline()`：

```js
CONFIG.isDifyReady = function (appId) {
  if (CONFIG.USE_MOCK) return false;              // 强制离线 → 一律不就绪
  if (!CONFIG.DIFY.baseUrl) return false;         // 无 baseUrl → 不就绪
  if (CONFIG.DIFY.proxyMode) return true;         // 反代模式 → 密钥在服务端，视为就绪
  var app = CONFIG.DIFY.apps[appId];
  return !!app && /^app-/.test(app.apiKey);       // 直连模式 → apiKey 须以 app- 开头
};

CONFIG.isOnline = function () {
  if (CONFIG.USE_MOCK) return false;
  if (CONFIG.DIFY.proxyMode) return !!CONFIG.DIFY.baseUrl;
  return Object.keys(CONFIG.DIFY.apps).some(function (k) { return CONFIG.isDifyReady(k); });
};
```

**排查提示**：如果页面显示"离线演示模式"但你认为配置正确，首先检查 `apiKey` 是否以 **`app-`** 开头 —— 前缀不对会被判定为未就绪。

## 七、常见连接问题排查

### 问题 1：课程沙箱返回 502（**已实测确认**）

**现象**：配置沙箱地址后页面进入离线模式；或 `demo-check.js` 报 `/v1/parameters` 不可达。

**验证命令**：

```bash
curl -s -m 5 -o /dev/null -w "%{http_code}\n" --noproxy '*' \
  http://123.249.115.157:48823/v1/parameters
```

**实测结果**：`502` —— 沙箱网关后的 Dify 实例已下线。

**结论与对策**：**不要依赖沙箱**。切换到本地契约桩：

```bash
node tools/demo-mode.js local-mock
node tests/mock-dify-server.js --port 8080 --serve .
```

---

### 问题 2：`localhost` 请求被代理劫持返回 502（**本方案踩过的坑**）

**现象**：桩服务明明在运行，但浏览器/`curl` 访问 `http://localhost:8080` 返回 502 `upstream connect failed`。

**根因**：本机配置了 HTTP 代理（`HTTP_PROXY` / `HTTPS_PROXY` 环境变量），`curl` 与部分浏览器配置会把 **`localhost` 也走代理**，而代理无法回连本机 8080 端口。

**对策（三选一）**：

1. **统一使用 `127.0.0.1` 而非 `localhost`** —— 本方案所有配置（`tasks.json`、`launch.json`、`config.local.js`、`demo-check.js`）已全部使用 `127.0.0.1`，规避该问题
2. 命令行测试时加 `--noproxy '*'`：
   ```bash
   curl -s --noproxy '*' http://127.0.0.1:8080/index.html -o /dev/null -w "%{http_code}\n"
   ```
3. 设置环境变量绕过代理：
   ```bash
   export NO_PROXY="127.0.0.1,localhost"
   # Windows PowerShell:
   $env:NO_PROXY = "127.0.0.1,localhost"
   ```

---

### 问题 3：端口 8080 被占用

**现象**：服务启动报 `EADDRINUSE: address already in use :::8080`。

**排查**：

```bash
# Windows
netstat -ano | findstr :8080
# 找到 PID 后
taskkill /PID <PID> /F
```

**对策**：换端口（三处需同步修改）：

```bash
node tests/mock-dify-server.js --port 8081 --serve .
node tools/demo-mode.js local-mock   # 然后手工把 config.local.js 的 8080 改为 8081
```

> 或直接用 `demo-check.js --port 8081` 体检新端口。

---

### 问题 4：页面显示「离线演示模式」，但期望是在线模式

**排查顺序**：

1. **确认 `config.local.js` 存在且 baseUrl 正确**
   ```bash
   node tools/demo-mode.js status
   # 期望：当前 js/config.local.js 模式：local-mock（本地契约桩）
   ```

2. **确认 `apiKey` 以 `app-` 开头** —— 这是 `isDifyReady()` 的硬性判定条件，前缀不对会被判为未就绪

3. **确认 `USE_MOCK` 未被设为 `true`** —— `USE_MOCK: true` 会强制走离线引擎

4. **打开浏览器开发者工具 → Network 面板**，筛选 `v1`，观察是否有请求发出：
   - **无请求** → 前端判定未就绪（回到第 2、3 步）
   - **请求 401** → `apiKey` 与服务端不匹配（本地桩模式下核对 §3.2 的 Key 表）
   - **请求 CORS 报错** → 见问题 5
   - **请求超时/失败** → 服务未启动或端口不符（回到问题 3）

5. **强制刷新页面**（`Ctrl+Shift+R`）—— `config.local.js` 有浏览器缓存

---

### 问题 5：CORS 跨域错误（`has been blocked by CORS policy`）

**根因**：浏览器的同源策略。若页面在 `127.0.0.1:8080` 而 API 在另一个源（不同端口或域名），浏览器会拦截。

**对策**：

- **本地桩模式**：桩服务与静态站点**同端口 8080**，天然同源，不会出现此问题
- **直连真实 Dify**：需在 Dify 侧配置 CORS 白名单，允许前端来源（如 `http://127.0.0.1:8080`）
- **生产环境**：改用反向代理模式（`proxyMode: true`），由 Nginx 同源转发

---

### 问题 6：SSE 流式输出卡住不返回

**现象**：对话类应用（医师咨询 / AI 助手）长时间无响应。

**排查**：

1. **`timeout` 是否过小** —— 大模型推理较慢，建议保持 `60000` 及以上
2. **代理是否缓冲了流式响应** —— 反向代理场景下 Nginx 需关闭缓冲：
   ```nginx
   proxy_buffering off;
   proxy_cache off;
   proxy_set_header Connection '';
   proxy_http_version 1.1;
   ```
3. **本地桩模式下不会出现此问题** —— 桩服务直接按 SSE 事件序列逐条推送

---

### 问题 7：`preLaunchTask` 未识别 / F5 后浏览器打不开

**现象**：F5 后一直停在"正在启动任务"，浏览器不弹出。

**根因**：VS Code 依靠 `problemMatcher.background` 的 `beginsPattern` / `endsPattern` 判断后台服务是否就绪。若桩服务的启动输出文案被改动，正则匹配失败就会一直等待。

**对策**：

- 确认 `tasks.json` 中的 `endsPattern: "按 Ctrl\\+C 停止"` 与桩服务实际输出文案一致
- 临时绕过：先手动运行 `演示 · 启动本地 Dify 契约桩` 任务，待服务就绪后，再单独运行调试配置（把 `launch.json` 中的 `preLaunchTask` 暂时删掉）

---

### 问题 8：页面图表不显示 / 部分交互失效（CSP 拦截内联脚本）★ 已修复

**现象**：页面能正常打开、数据也加载出来了，但**图表区域空白**（近 7 日打卡趋势折线、热门资讯浏览量条形、生活方案进度环形），或错误态重试按钮点击无反应。

**根因（实测确认）**：

桩服务 `tests/mock-dify-server.js` 第 184 行与生产 `snippets/security-headers.conf` 第 29 行均下发：

```
Content-Security-Policy: default-src 'self'; script-src 'self'; ...
```

`script-src 'self'` **不含** `'unsafe-inline'`，因此页面中**内联 `<script>` 会被浏览器直接拦截、不执行**。而项目原有 8 个页面末尾各有一段内联脚本，承载的正是上述图表渲染与错误态保护逻辑：

| 页面 | 内联脚本职责 | 受影响表现 |
|---|---|---|
| `checkin.html` | 近 7 日打卡趋势折线图 | 折线图空白 |
| `health-news.html` | 热门资讯浏览量条形图 | 条形图空白 |
| `life-plan.html` | 生活方案进度环形图 | 环形图空白 |
| `personal.html` | 个人中心进度环形图 | 环形图空白 |
| `admin.html` | 管理后台数据表错误态 | 错误态提示不出现 |
| `doctor.html` | 医师列表加载/空态/错误态 | 空态与重试失效 |
| `help.html` | 帮助中心 FAQ 错误态 | 错误态提示不出现 |
| `risk-prediction.html` | 历史评估错误态重试 | 重试按钮无反应 |

**实测证据**（修复前，用真实 Chromium 加载 3 个受影响页面）：

```
[checkin.html]     CSP 拦截 1 条 → 'script-src 'self''
[health-news.html] CSP 拦截 1 条 → 'script-src 'self''
[life-plan.html]   CSP 拦截 1 条 → 'script-src 'self''
结论：检测到 3 条 CSP 内联脚本拦截
```

**修复方式**：将内联脚本**抽取为外链 `.js` 文件**（而非放宽 CSP），既保留严格的安全策略，又同时修复演示与生产环境。

```bash
cd "C:/Users/mazit/Desktop/2026秋/实训2/01-源代码/diabetes-assistant"
python extract_inline_scripts.py           # 预演，确认替换方案
python extract_inline_scripts.py --apply   # 执行（自动备份到 _backup_inline_20260917/）
```

抽取结果：新增 `js/pages/<页面>-init.js` 共 8 个，HTML 中内联块替换为：

```html
<script src="js/pages/checkin-init.js" defer></script>
```

> **为什么用 `defer` 是安全的**：原内联块位于所有 `defer` 脚本之后、`</body>` 之前，且内部逻辑统一包在 `document.addEventListener('DOMContentLoaded', ...)` 中。改为 `defer` 后脚本仍在 `DOMContentLoaded` 之前执行，监听器照常注册并触发，**执行时机与顺序均不变**。

**修复后复验**：CSP 违规 **0 条**，三个图表全部渲染成功（趋势图与环形图为 SVG，条形图为 div 结构）。
